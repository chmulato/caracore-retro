O Problema de Bancos Pesados Locais

Muitos projetistas tentam resolver a autonomia das lojas instalando servidores de banco de dados relacionais completos (como PostgreSQL ou SQL Server Express) localmente no computador do caixa. Essa abordagem gera um gargalo operacional imenso. Servidores de banco de dados tradicionais exigem processos de background gerenciando conexões TCP/IP locais, alocação de sockets virtuais e tarefas de manutenção pesadas (como vacuum ou logs de transações crescentes) que travam caixas modestos e causam falhas de conexão interprocesso se o serviço travar.

O SQLite como Banco de Dados de Produção na Borda

Muitos engenheiros encaram o SQLite apenas como um banco de dados de brinquedo, útil apenas para testes unitários ou protótipos rápidos. Essa visão é equivocada. O SQLite é o banco de dados mais distribuído do planeta, rodando de forma estável no núcleo de bilhões de smartphones, navegadores e sistemas embutidos industriais.

No caixa de varejo físico, a maior vantagem do SQLite é sua simplicidade operacional: ele é apenas um arquivo em disco. Não há serviço ou daemon rodando em segundo plano, não há consumo de conexões de rede locais (`localhost`) e não há consumo ocioso de memória RAM. O banco é carregado em processo direto na aplicação local.

Tunagem de Concorrência: Ativando o Modo WAL

Por padrão, o SQLite opera em modo DELETE, que bloqueia leituras enquanto ocorre uma escrita (modo de bloqueio exclusivo). Para sistemas que precisam imprimir cupons e sincronizar dados em segundo plano enquanto registram itens na tela, isso pode causar o erro `SQLITE_BUSY`.

Resolvemos esse comportamento com três configurações fundamentais via propriedades do driver JDBC:

  1. Modo WAL (Write-Ahead Logging): `journal_mode=WAL`. Permite que múltiplos leitores acessem o banco simultaneamente enquanto uma escrita está em andamento.
  2. Sincronização Normal: `synchronous=NORMAL`. Reduz o número de vezes que os dados são forçados fisicamente ao disco rígido (fsync), aproveitando o buffer de gravação do sistema operacional sem comprometer as transações ACID.
  3. Espera Ativa (Busy Timeout): `busy_timeout=5000`. Define que a aplicação aguarde até 5 segundos para obter o lock de escrita antes de estourar um erro.

Como Funciona o WAL e o Checkpoint

No modo WAL, o SQLite não altera o arquivo `.db` principal diretamente a cada transação de escrita. Em vez disso, ele grava os commits de forma sequencial rápida em um arquivo auxiliar de log chamado `.db-wal` (Write-Ahead Log). Um segundo arquivo, `.db-shm` (Shared Memory), é gerado temporariamente para mapear o log em memória e agilizar as leituras concorrentes.

Enquanto as escritas entram no arquivo de log, os leitores consultam o arquivo `.db` principal e o log em andamento, garantindo leituras limpas sem sofrer nenhum bloqueio. Periodicamente, o SQLite executa um processo automático chamado Checkpoint, que transfere com segurança os dados acumulados do arquivo de log `.db-wal` de volta para o arquivo `.db` principal, esvaziando o log sem interromper a operação de vendas.

Limitações Reais: Onde o SQLite Não Serve

O SQLite é a ferramenta perfeita para a borda autônoma, mas não é um martelo de ouro. Reconhecer seus limites impede decisões erradas de arquitetura:

  • Escrita Concorrente Centralizada: O SQLite suporta apenas um único escritor ativo por arquivo. Se você tentar apontar o banco de 50 caixas de caixas na rede local para o mesmo arquivo de rede, o banco entrará em bloqueio infinito e travará o faturamento. O SQLite exige um arquivo exclusivo por terminal de caixa.
  • Segurança e Permissões: Ele não gerencia usuários, perfis de acesso ou restrições internas de conexões TCP. A segurança dos dados é delegada diretamente às permissões de sistema operacional (controle de acesso de leitura e escrita da pasta física do arquivo no sistema de arquivos local do caixa).
  • Sem Servidor Nativo: Não possui suporte nativo a comunicações em rede. A comunicação centralizada e consolidada das transações com a nuvem central deve ser inteiramente resolvida na camada de aplicação (através do padrão Transactional Outbox que trataremos no Canto VI).

Código na Prática: Evitando Travamentos no Spring

Apenas mudar a URL do properties não impede todos os problemas. Na aplicação, as transações de gravação precisam ser rápidas e isoladas. Veja o exemplo de serviço com controle de transação e retentativa de gravação para contornar o erro `ObjectOptimisticLockingFailureException` (que ocorre se duas transações concorrentes tentarem atualizar o mesmo registro de fila Outbox no SQLite ao mesmo tempo): 

@Service
public class VendaService {

    @Autowired
    private VendaRepository repo;

    @Transactional
    public Venda concluirVendaComRetry(Venda venda) {
        int tentativas = 3; // Padrão equilibrado para contornar eventuais conflitos temporários de lock
        while (tentativas > 0) {
            try {
                return repo.save(venda);
            } catch (ObjectOptimisticLockingFailureException | DataIntegrityViolationException e) {
                tentativas--;
                if (tentativas == 0) throw e;
                try { Thread.sleep(100); } catch (InterruptedException ie) { Thread.currentThread().interrupt(); }
            }
        }
        return null;
    }
}

⚖️ O Veredito da Bancada (Técnico vs. Negócios)

💻 Para Técnicos (A Baseline)

Configure o datasource no application.properties:
spring.datasource.url=jdbc:sqlite:pdv.db?journal_mode=WAL&synchronous=NORMAL&busy_timeout=5000. O modo WAL cria arquivos extras `.db-wal` e `.db-shm` para gerenciar o log de gravação compartilhado. Isso garante isolamento atômico ACID completo em transações concorrentes na borda com latência de gravação de apenas ~0.8 milissegundos.

👔 Para Negócios (O Retorno)

Zero custos de licença ou infraestrutura para servidores de banco locais na loja. O banco é imune a quedas de energia: se a tomada for desligada de repente no meio de uma venda, os arquivos não se corrompem e a operação volta exatamente de onde parou.

Conclusão da Persistência Local

O SQLite tunado em modo WAL é a base ideal para prover persistência local estável e leve para pontos de venda físicos autônomos. Ele equilibra segurança ACID completa com simplicidade e consumo zero de recursos ociosos.
